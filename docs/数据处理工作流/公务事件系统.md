# 公务事件系统

> 本文档说明公务事件系统的目录构成、事件表写法、入队与去重规则、结算语法、全局数值、构建流程与编写约定。教育区专属的养成事件规则见 [生长养成系统](./生长养成系统.md) 第 8 节。

## 1. 概述

公务事件是玩家在博士办公室执行「处理公务」指令时需要决断的事项。每次执行「处理公务」时，系统从待处理队列队首取出第一条存在可选选项的事件供玩家选择。玩家选定选项后，系统在处理公务的行动开始时结算该选项、记录履历并单独显示后果提示。

事件分类直接复用 `data/csv/Facility.csv` 中 `type == -1` 的部门区块编号，不另设分类表。当前数据中只有教育区（部门 `15`）包含事件，其他部门的无主体事件（`subject=0`）可按同一套表结构走默认入队链路，带角色主体的事件（`subject=1`）需注册部门提供者。

## 3. 事件表列与写法

每个事件 CSV 必须包含 5 行表头，每条有效数据行包含 28 列（8 个基本列与 4 组共 20 个选项列）。校验工具在文件少于 5 行、前 8 列名不符约定，或从第 6 行起首格（`cid`）非空行的字段数不等于 28 时报错，同时拒绝 UTF-8 BOM 以及 CRLF 与 LF 混用的行尾。首格为空的行会被校验工具整行跳过而不报错，但构建脚本会删掉空 `cid` 键并在载入配置时于 `game_config.py` 抛出 `KeyError`，因此每条有内容的数据行都必须填写 `cid`。

### 3.1 28 列定义

| 列名 | 类型 | 规则与说明 |
| --- | --- | --- |
| `cid` | str | 事件编号，每条有内容的数据行都必须填写且在本文件内唯一，不得含 `@`，构建时拼接文件名生成事件 `uid`（首格为空的行会被校验工具跳过，并在载入时抛出 `KeyError`） |
| `department` | int | 部门编号，必须是 `Facility.csv` 中 `type == -1` 的整数区块编号。非整数在构建时保留为字符串，`subject=1` 行不会被抽中，`subject=0` 行可能被默认提供者抽中并在 `push_official_event` 转整数时抛出 `ValueError` 中断当晚结算，提交数据前须运行校验工具 |
| `subject` | int | 主体类型，只能取 `0`（无角色主体）或 `1`（角色主体，`A1` 指向该角色）。`subject=0` 时校验工具拒绝 `CVE_A1` 与 `CVE_A2`，允许 `CVE_RI_...`、`CVE_A3\|<adv>_...` 与纯数字结算编号（默认提供者以 `chara_id=0` 入队，结算时纯数字结算以角色 `0` 博士为主体执行），运行时只有默认提供者读取该列 |
| `sub_key` | int | 部门内子桶键，`0` 表示本部门通用事件并由部门提供者解释含义，教育区取值见下文 |
| `once` | int | 整数，仅作作者标注，运行时代码不读取该列 |
| `weight` | int | 正整数基础权重，运行时非法值回退为 `1`（`get_event_weight`），抽取权重等于配置权重乘以前提权重 |
| `premise` | str | 触发前提，多项用 `&` 连接，各项必须是已注册前提名或 `CVP_` 表达式，`CVP_` 判定值必须为整数 |
| `text` | str | 事件正文，不能为空，文本校验规则见下文 |
| `option_1`~`option_4` | str | 选项正文，留空表示该选项不存在，留空时其对应 4 个附属列必须同步留空 |
| `option_1_premise`~`option_4_premise` | str | 选项前提，语法与 `premise` 相同，运行时不满足前提的选项置灰显示而非隐藏 |
| `option_1_reason`~`option_4_reason` | str | 选项置灰原因，填写了 `option_N_premise` 的选项必须填写本列 |
| `option_1_tip`~`option_4_tip` | str | 后果提示，每个有效选项都必须填写，只写方向不写数值，在选定并结算后单独显示 |
| `option_1_effect`~`option_4_effect` | str | 选项结算，多项用 `&` 连接，写法见第 6 节 |

教育区（部门 `15`）的 `sub_key` 取值如下：`0` 覆盖阶段 `101`~`103`，`101`/`102`/`103` 对应各自阶段，`104` 为成年桶（仅允许成年结算显式推入的 `通用1`、`通用2`、`通用59`、`通用60`），`200` 为期末桶（`education_constant.SEMESTER_EVENT_SUB_KEY`）。

### 3.2 文本、选项与校验规则

运行离线校验的命令如下：

```bash
python tools/official_event_check.py          # 校验并打印统计报告
python tools/official_event_check.py --full   # 额外校验条数下限
python tools/official_event_check.py --quiet  # 仅输出错误或通过摘要
```

校验工具与运行时共同约束以下规则：

1. **占位符与标点**：校验工具仅对 `text` 与 `option_N` 执行文本检查，允许使用的占位符以校验工具的 `TEXT_PLACEHOLDER`（`talk.py` 替换表的子集）为准，同时禁止裸花括号、英文双引号与英文逗号（中文句内应使用全角逗号）。`option_N_reason` 与 `option_N_tip` 不受此项文本检查，但在绘制时同样会经过格式化替换，编写时也应避免裸花括号与非法占位符。
2. **正文查重**：`text` 去掉占位符后的前 15 字（`TEXT_DUP_LEN = 15`）不得与同文件内其他条目重复。
3. **选项数量与兜底**：每条事件至少填写 2 个选项，且至少 1 个选项不带前提。每次弹出事件时，界面将全部选项（含置灰选项）的显示顺序随机洗牌，结算、履历与后果展示仍按 CSV 原序号 `1`~`4` 执行（`official_event_panel.py`）。若运行时某条事件的所有选项均不可选，系统跳过该事件并向履历写入选项 `0`，防止次日再次弹出。
4. **育儿室限制**：教育区子桶 `102`、`103`、`104`、`200` 的正文不得出现「育儿室」，登记在 `DORM_TEXT_ALLOW` 白名单中的条目（当前仅 `幼女.csv` 的 `cid=5`）除外。
5. **期末桶前提限制**：教育区期末桶（`sub_key = 200`）的事件前提与选项前提不得以任何形式读取养成数值 `4`、`5`、`6`、`9`、`23`，因为推送时刻这些值均已重置或恒定。校验工具只拦截部门 `15`、`sub_key = 200` 行中 `premise` 与四个 `option_N_premise` 里的 `CVP_A1_Growth|N_` 与 `CVP_A2_Growth|N_` 形式，对 `CVP_A3|<adv>_Growth|...` 不做拦截，作者须手动避免。
6. **未成年能力与素质校验**：在教育区子桶 `0`、`101`、`102`、`103`、`200` 中，校验工具仅拦截匹配 `CVE_A1_A|`、`CVE_A1_T|`、`CVE_A2_A|`、`CVE_A2_T|` 的结算项。其余能改写能力或素质的写法须由作者手动避免（见第 10 节）。
7. **成年桶白名单**：教育区 `sub_key = 104` 只允许 `ADULT_EVENT_UID_SET` 内的四个 `uid`（`通用1`、`通用2`、`通用59`、`通用60`）。

## 4. uid、履历与改名迁移

### 4.1 uid 生成与履历键

构建脚本取文件名第一个 `.` 之前的部分（`file_name.split(".")[0]`），与 `cid` 无分隔符直接拼接生成事件 `uid`（`buildconfig.py` 与 `auto_build_config.py`）。例如 `通用.csv` 的 `cid=1` 生成 `通用1`，修改文件名或重排 `cid` 都会直接改变事件 `uid`。因为没有分隔符，不同文件与 `cid` 的组合可能生成同一个 `uid`（例如 `部门1.csv` 的 `cid=2` 与 `部门.csv` 的 `cid=12` 都会生成 `部门12`），带额外点号的文件名也会共用第一个 `.` 之前的前缀。载入配置时，按文件名排序靠后的条目会静默覆盖先载入的同名 `uid`，两条记录仍会留在部门与子桶索引列表中。校验工具只在单个文件内检查 `cid` 唯一，不跨文件查重。作者必须保证所有事件表生成的 `uid` 全局唯一，不在文件名中使用额外点号，且文件名与 `cid` 均不得包含 `@`。

所有事件在结算后一律写入履历（跳过无可选选项的事件也会写入选项 `0`）。只要所有 `uid` 均不含 `@`，履历键就能按主体准确去重：

- 主体角色存在且持有 `growth.child` 数据时，写入 `growth.child.event_history[uid] = {"time": 游戏时间, "choice": 选项序号}`。
- 主体编号为 `0`（无主体部门事件）、主体角色无 `growth.child` 数据或主体角色不存在时，写入全局履历 `base.official_history`（经 `official.history()`、`official.done()`、`official.record()` 读写）。键由 `get_history_key` 生成：主体编号为 `0` 时为 `uid`，否则为 `uid@<角色id>`。`@` 是保留分隔符，若无主体事件的 `uid` 写成 `X@5`，会与角色 `5` 的 `X` 撞键，且读档迁移按第一个 `@` 拆分，因此文件名与 `cid` 均不得包含 `@`。

### 4.2 读档改名迁移与两道守卫

`Script/Core/save_handle.py` 定义映射表 `_OFFICIAL_EVENT_UID_MIGRATE = {"萝莉1": "期末17", "萝莉20": "期末18", "萝莉26": "期末19"}`。读档时，`_migrate_official_event_history` 对每个角色的 `growth.child.event_history`（经 `growth.normalize_legacy`）以及全局履历 `official.history()` 执行迁移，拆分键中的 `@<角色id>` 后缀后替换 `uid`。

迁移逻辑包含两道守卫，重复读档具有幂等性：

1. **守卫 1**：若原 `uid` 不在 `_OFFICIAL_EVENT_UID_MIGRATE` 中，或原 `uid` 仍在 `game_config.config_official_event` 中存在，则跳过该键。
2. **守卫 2**：若迁移后的新键在当前履历字典中已有记录，则跳过该键。此时旧键留在字典中，履历面板查不到其配置时会自动跳过。

### 4.3 队列不迁移与严禁复用旧 uid

待处理队列 `base.official_queue` 不参与上述改名迁移。读取队列条数或出队时，`clean_official_event_queue` 会删除 `uid` 不在配置中或主体角色不存在的项，并将互动对象不存在的项把 `partner_id` 重置为 `0`。

若后续编辑事件表时复用了某个已退役的旧 `uid`（例如新建一条 `萝莉1`），会引发两类错误：

1. 新建的 `萝莉1` 重新进入 `game_config.config_official_event`，触发守卫 1 阻断旧存档履历的改名。该角色的履历保留旧 `萝莉1`，导致新写的 `萝莉1` 被误判为已触发，同时 `期末17` 会再次触发。
2. 队列中残留的旧 `萝莉1` 条目因为能在配置中查到而通过 `clean_official_event_queue` 检查，出队时会弹出完全无关的新事件。

因此必须遵守硬性规则：**严禁复用已退役的 `uid`，新增事件一律使用新的 `cid`**。

## 5. 每晚入队流程

### 5.1 跨天结算执行顺序

`Script/Settle/past_day_settle.py` 中 `update_new_day()` 的执行顺序如下：

1. `sex_class_handle.clean_expired_temp_class()`：清理过期临时实操课。
2. 逐角色刷新循环：处理食物变质、清理过期翘课标记、排卵兜底、刷新每日娱乐、替换照料卵时段、套用日程模板、刷新生理周期、清理助理与食物标记、增加欲望以及周日粉红凭证。
3. `semester_handle.settle_semester_change()` 与 `growth_event_handle.push_semester_event_for_list(...)`：学期切换冻结成绩单并推送期末事件。
4. 基地资源更新、导航到达判定、周日外交与感染率结算、周一助理轮换。
5. `growth_event_handle.push_birthday_event()`：将今日过生日女儿的生日事件插到队首。此步排在日常派发之前，防止日常派发重复抽取同一条生日事件。
6. `official_event_handle.check_new_day_official_event()`：筛选并入队今日公务事件。逐角色刷新循环只遍历 `roster.active()` 与玩家（`0`），因此此步排在刷新之后只保证在编角色与玩家的前提读到当日刷新后的状态。教育区每日名单中包含的离线 `101` 婴儿与 `102` 幼女不在刷新循环内。

### 5.2 提供者注册表、默认提供者与入队控制

`official_event_handle.py` 通过三个装饰器解耦公共链路与各部门逻辑：

- `register_provider(department)`：注册到 `EVENT_PROVIDER`，提供者自行节流并返回 `[{"uid": str, "chara_id": int, "partner_id": int}, ...]`。
- `register_capacity(department)`：注册到 `EVENT_CAPACITY`，返回该部门需要的额外队列容量。
- `register_title(department)`：注册到 `EVENT_TITLE`，根据队列元素返回事件抬头文本，未注册时抬头为部门名（`get_department_name`）。

`init_provider()` 在函数内部导入各部门模块以规避循环导入。未注册自定义提供者的部门走默认提供者，但仅添加 CSV 只对 `subject=0`（无主体）事件生效，这类事件以博士（角色 `0`）为判定主体并以 `chara_id=0` 入队。未注册部门中的 `subject=1` 事件会被默认提供者跳过，永远不会入队且不报错。部门需要 `subject=1`（角色主体）事件时，必须通过 `register_provider` 注册负责挑选主体的提供者，并在 `init_provider()` 中新增导入。

默认提供者 `get_default_department_pick_list()` 扫描所有未在 `EVENT_PROVIDER` 中注册的部门，并以博士（角色 `0`）作为判定主体。它对每条事件调用 `judge_event_can_enqueue(uid, 0)` 并跳过 `subject == 1` 的条目。剩余候选按 `get_event_weight(uid) * now_weight` 加权抽取，全部默认部门每日合计最多选出 `DEPARTMENT_EVENT_DAILY_MAX = 2` 条。

`check_new_day_official_event()` 在配置为空时立即返回。配置非空时，它依次调用各已注册提供者（单个提供者抛出异常时打印调试信息并跳过该部门），再合并默认提供者的结果。合并后的候选列表经 `random.shuffle` 打散，系统取前 `OFFICIAL_EVENT_DAILY_MAX = 8` 条依次调用 `push_official_event`。

`push_official_event(uid, character_id, partner_id, to_front=False, ignore_capacity=False)` 只校验配置存在性与队列容量：

- 队列上限为 `get_queue_max() = max(12, 6 + Σ各部门容量提供者返回值)`。
- 队列已满时丢弃新事件，不挤掉队列中已有事件。
- `to_front=True` 将事件插到队首且跳过容量上限检查。`ignore_capacity=True` 将事件追加到队尾且跳过容量上限检查。

教育区（部门 `15`）的每日提供者从 `get_growth_event_character_list()` 获取处于 `101`~`103` 阶段的玩家女儿。其中 `101` 婴儿与 `102` 幼女离线、不要求在 `roster` 中，`103` 学员要求在 `roster` 中。提供者先打乱候选名单，再按每名女儿每日 `70%` 概率、至多 `1` 条抽取候选。教育区容量提供者按名单内每名女儿贡献 `4` 条额外容量。专项推送包括仅面向 `103` 学员的期末事件、插队首的生日事件、插队首的毕业典礼 `通用1` 与成年纪念 `通用2`（依赖 `103` 到 `104` 的阶段转换保证幂等，不调用 `judge_event_can_enqueue`），以及以 `ignore_capacity=True` 追加到队尾的 `通用59` 与 `通用60`。

### 5.3 去重职责边界

`judge_event_can_enqueue(uid, character_id)` 是全系统唯一同时检查配置存在性、履历去重（`judge_event_done`）与队列去重（`judge_event_already_in_queue`，按 `(uid, chara_id)` 匹配）的守卫函数（配置存在性也会在 `push_official_event` 与 `clean_official_event_queue` 中单独检查）。它只能看到本晚批次入队前的履历与队列状态。`check_new_day_official_event` 先汇总全部提供者的结果再逐条调用 `push_official_event`，入队循环与 `push_official_event` 均不对批次内重复做去重。

因此，除毕业典礼 `通用1` 与成年纪念 `通用2`（依赖 `103` 到 `104` 的阶段转换只发生一次）外，每个提供者与推送入口都必须对候选调用 `judge_event_can_enqueue`，并保证单次批次内对同一 `(uid, chara_id)` 至多返回一次，且不同提供者不返回相同配对。教育区（部门 `15`）的每日提供者对每个女儿至多选出一条候选，不会在批次内产生重复配对。默认提供者只在全部事件的生成 `uid` 互不冲突时满足批次内不重复。毕业典礼 `通用1` 与成年纪念 `通用2` 不调用 `judge_event_can_enqueue`，依赖 `103` 到 `104` 的阶段转换只发生一次来避免重复推入。现有调用 `judge_event_can_enqueue` 的入口包括默认提供者、`growth_event_handle.py` 的日常候选收集、`通用59`/`通用60` 推送、生日推送与期末推送。

## 6. 效果与前提写法

### 6.1 结算串与前提串语法

结算串由 `official_event_handle.handle_effect_text()` 按 `&` 拆分后分发为三类：

1. **`CVE_RI_<类型>_<G|L|E>_<值>`**：罗德岛全局数值结算，在角色分支之前由 `handle_ri_effect` 处理。
2. **`CVE_A1_<类型>_<G|L|E>_<值>`、`CVE_A2_<类型>_<G|L|E>_<值>`、`CVE_A3|<adv>_<类型>_<G|L|E>_<值>`**：角色数值结算（完整形式 `CVE_<主体>_<类型>_<G|L|E>_<值>`，各段一律以 `_` 分隔，`<类型>` 可带 `|<子id>`，如 `F`、`X`、`A|3`、`Growth|10`），交给 `settle_behavior.handle_comprehensive_value_effect`。结算期间系统临时将主体交互对象设为事件 `partner_id`（使 `A2` 指向互动对象）并在 `finally` 中还原。结算使用一次性 `CharacterStatusChange`，不向界面输出具体数值。
3. **纯数字**：按编号在 `constant.settle_behavior_effect_data` 中调用对应的结算函数。

养成数值读写使用 `Growth|N`（编号定义在 `education_constant.py` 第 11 组）。`settle_behavior.handle_comprehensive_value_effect` 将运算符 `E` 分发到 `growth_handle.set_growth_value`，将 `G` 与 `L` 分发到 `growth_handle.change_growth_value`。两个写入入口都只写入四对性格倾向（`10`~`13`）与照料值（`20`，下限钳制为 `0`），其余编号会被静默忽略。

前提串中的 `CVP_` 由 `handle_premise.handle_comprehensive_value_premise` 求值：`RI` 主体在函数开头提前返回并经 `ri_value.get_ri_value` 取值，`A1` 指向主体自身，`A2` 指向当前交互对象（事件判定期间通过 `activity.target_as` 绑定为 `partner_id`），`A3|<adv>` 指向指定角色（未拥有该角色时返回 `0`）。

### 6.2 校验限制与互动对象子串规则

`tools/official_event_check.py` 对结算串执行以下检查：

- 每项必须是 `constant_effect.py` 中已定义的结算编号或 `CVE_` 表达式。
- `CVE_` 表达式按 `_` 拆分后至少包含 4 段（含 `CVE` 前缀），主体只能是 `A1`、`A2`、`A3...` 或 `RI`，倒数第二段的运算符只能是 `G`、`L`、`E`。校验工具不检查类型段，也不检查 `A3|<adv>` 中的 `<adv>` 是否为整数。
- 数值格式方面，运行时要求 `RI` 与 `Growth` 的值为数字（允许小数），其余结算值为整数。校验工具只检查 `RI` 表达式的值为数字、以及不含 `Growth` 字串的表达式的值为整数，对含 `Growth` 的表达式不做数值校验。若含 `Growth` 的结算写入非数字，结算时在 `float()` 处会抛出 `ValueError` 并中止结算。
- 结算使用 `A2` 时，事件主前提 `premise` 必须包含 `self_have_sibling_child` 或 `self_have_classmate`，否则报错。
- 当事件的 `subject=0` 时，校验工具拒绝任何 `CVE_A1` 或 `CVE_A2` 结算项。
- 在教育区未成年子桶（`0`、`101`、`102`、`103`、`200`）中，仅拦截匹配 `CVE_A1_A|`、`CVE_A1_T|`、`CVE_A2_A|`、`CVE_A2_T|` 的结算项，不拦截 `A3|<adv>` 表达式、不带 `|` 的写法或纯数字结算编号。

教育区的 `growth_event_handle.get_event_partner()` 通过子串检查事件 `premise` 是否包含 `self_have_sibling_child` 或 `self_have_classmate` 来选择互动对象。新增前提名时不得包含这两个名称作为子串。

### 6.3 内置复杂结算编号

| 结算编号 | 常量名 | 行为与约束 |
| --- | --- | --- |
| `3002` | `OFFICIAL_EVENT_ACCEPT_RECRUIT` | 调用 `recruit_service.recruit_new_chara()` 接收一名待确认招募干员 |
| `3003` | `OFFICIAL_EVENT_TEMP_COMMISSION` | 调用 `field_commission_function.create_temp_commission` 生成临时外勤委托 |

结算 `3003` 以固定参数调用 `create_temp_commission`，后者会以追加模式直接写入 `data/csv/Commission.csv`。委托描述中换行须写作双字符 `\n` 且不得包含英文逗号的约束，适用于修改该结算函数或 `create_temp_commission` 的代码维护者，而非 CSV 事件作者。委托需求与奖励遵循外勤系统的前缀语法（如 `r_资源id_数量`、`声望_势力id_值`），不可与 `CVE` 语法混用。

## 7. 全局数值 RI

`Script/System/Official_Event_System/ri_value.py` 定义了 7 类罗德岛全局数值：

| 类型写法 | 含义 | 可读 | 可写 | 写入夹逼与说明 |
| --- | --- | --- | --- | --- |
| `R\|<资源id>` | `Resource.csv` 素材资源 | 是 | 是 | 取整，下限 `0` |
| `Rep\|<势力id>` | 势力声望 | 是 | 是 | 直接写入 |
| `Fac\|<设施cid>` | 设施等级 | 是 | 否 | 只读 |
| `Work` | 待处理公务量 | 是 | 是 | 钳制在 `[0, 总工作量]`，保留 1 位小数 |
| `Eff` | 基地效率 | 是 | 是 | 钳制在 `50`~`200`（`EFFECTIVENESS_MIN`/`EFFECTIVENESS_MAX`），保留 1 位小数 |
| `Power` | 电力储量 | 是 | 是 | 取整，下限 `0` |
| `People` | 当前干员数 | 是 | 否 | 只读 |

只读集合为 `READ_ONLY_TYPE_SET = {"Fac", "People"}`。运行时对只读类型的写入会被忽略并打印调试信息。校验工具目前只检查 `RI` 表达式的段数、运算符与数值格式，不会拦截对只读类型的写入。

## 8. 构建与加载

`buildconfig.py` 与 `auto_build_config.py` 各自包含一份公务事件构建分支（两者并非完全相同的拷贝，例如对短行的处理不同），遍历 `data/official_event/` 下所有 `.csv` 文件合并生成 `Official_Event` 表并输出为 `data/Official_Event.json`。修改该构建逻辑时必须两处同步修改。`data/Official_Event.json` 属于未跟踪的构建产物（`.gitignore` 忽略 `data/*.json`）。

构建脚本会删除所有空字符串单元格对应的键（`if not len(row[k]): del row[k]`）。`game_config.load_official_event()` 直接保存每条事件的原始字典，并建立按 `uid`、按部门（`config_official_event_by_department`）与按 `(department, sub_key)`（`config_official_event_by_sub_key`）的三张索引表。运行时读取可选列必须使用 `.get()`。

## 9. 事件条数下限

### 9.1 校验工具配置阈值

`tools/official_event_check.py` 配置了条数下限表 `MIN_COUNT = {"婴儿": 50, "幼女": 70, "萝莉": 67, "通用": 56}`，仅在 `--full` 模式下执行校验。统计 `通用.csv` 时不计入 `sub_key = 104` 的成年后事件。`萝莉` 项为 `67`，是因为 `萝莉1`、`萝莉20`、`萝莉26` 迁入期末桶后从规划目标 `70` 中扣除了 `3` 条。

当前数据中 `婴儿.csv` 有 `48` 条、`幼女.csv` 有 `30` 条、`萝莉.csv` 有 `59` 条。在当前数据上执行 `--full` 会报告这三个文件低于 `MIN_COUNT`。

### 9.2 规划估算与运行时差异

下表为设定 `MIN_COUNT` 时的规划估算，而非运行时消耗的硬上界。估算假设每名女儿不开启成长停滞、不使用成长加速药、各阶段按 `pregnancy_constant.py` 累计阈值 `30` / `90` / `150` 固定经历 `30` / `60` / `60` 天（合计 `150` 天）、每天至多走 `1` 次日常抽取，且跨阶段通用池（`sub_key = 0`）按设计权重在各阶段分担 `25%` 抽取量：

| 文件与阶段 | 假设阶段天数 | 估算消耗 | 20% 盈余估算下限 | 规划目标（`MIN_COUNT`） | 估算消耗率 / 盈余 | 70% 日概率下均值盈余 |
| --- | --- | --- | --- | --- | --- | --- |
| `婴儿.csv`（101 婴儿） | 30 | 22.5 | 29 | 50 | 45% / 55% | 68.5% |
| `幼女.csv`（102 幼女） | 60 | 45 | 57 | 70 | 64% / 36% | 55% |
| `萝莉.csv`（103 学员） | 60 | 45 | 57 | 67（目标 70 减迁入期末桶的 3 条） | 64% / 36%（按 70 计） | 55%（按 70 计） |
| `通用.csv`（`sub_key = 0`） | 150 | 37.5 | 47 | 56 | 67% / 33% | 53% |

按该估算，维持至少 `20%` 盈余的条数下限为 `⌈估算消耗 / 0.8⌉`，即 `29` / `57` / `57` / `47`。

实际运行与上述规划假设存在以下差异：

- 成长停滞（素质 `28`）会让 `102` 幼女或 `103` 学员无限期停留在本阶段并继续每日抽取，因此消耗没有固定上界。
- 成长加速药会缩短各阶段的持续天数。
- 生日事件（`通用3`）在日常抽取之外直接推入队列。
- 实际抽取只对当前满足前提且未触发的条目加权（`get_event_weight(uid) * now_weight`），通用池占比会随池子消耗与前提权重变化。按满池 CSV `weight` 剔除 `CVP_A1_T|101_E_0` 与 `CVP_A1_T|103_E_0` 排除项后，`通用.csv` 的权重占比在婴儿期为 `9.7%`（65/673）、幼女期为 `42.1%`（229/544）、学员期为 `26.1%`（217/831）。

## 10. 编写约定

除「育儿室用词限制」以及未成年子桶对特定能力/素质表达式的拦截外，以下权重、数值幅度与负面结果边界均为编写约定，校验工具不全面拦截：

- **权重约定**：阶段日常事件 `9`~`12`，里程碑事件 `15`~`25`，跨阶段通用事件 `3`~`5`。压低跨阶段权重用于控制通用池的抽取占比。
- **数值幅度约定**：未成年阶段好感 `+5`~`+30` / `-5`~`-20`，信赖 `+2`~`+6`，性格倾向 `±1`~`±4`，照料值 `+1`~`+5`。成年阶段（`sub_key = 104`）好感 `+80`~`+200`，信赖 `+10`~`+20`。
- **负面结果边界**：选错选项只造成性格倾向偏离预期或好感小幅下降，不扣除能力或素质。校验工具只在教育区子桶 `0`、`101`、`102`、`103`、`200` 中拦截 `CVE_A1_A|`、`CVE_A1_T|`、`CVE_A2_A|`、`CVE_A2_T|`，对 `CVE_A3|<adv>` 能力/素质表达式、不带 `|` 的 `CVE_A1_A_...` / `CVE_A1_T_...` 以及纯数字结算编号不做拦截，作者须手动避免使用。
- **跨阶段事件约定**：`sub_key = 0` 中不适合婴儿阶段的内容需在 `premise` 中加上 `CVP_A1_T|101_E_0`。跨阶段正文不得绑定具体住处，因为婴儿住育儿室，幼女起住自己的宿舍。
- **育儿室用词约定**：教育区子桶 `102`、`103`、`104`、`200` 的正文不得出现「育儿室」。确需描写搬离育儿室的条目必须在 `tools/official_event_check.py` 的 `DORM_TEXT_ALLOW` 中登记。
