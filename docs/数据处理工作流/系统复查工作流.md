# 系统复查工作流

本文档讲对一个**已经实现完成的系统**反复做全面复查的来龙去脉：为什么要一轮一轮地查、每轮怎么走、产出什么、积累了哪些经验、什么时候可以停。以生长养成系统的第五~十一轮复查作为贯穿案例。

---

## 1. 为什么要多轮复查

一个大系统做完之后，按函数写的单元测试全绿，不代表它在游戏里真的能跑通。生长养成系统四期实施、收尾总检查（2026-09-09，641 条断言）之后，第五轮复查仍发现「教师—学生」这条主链在行为循环里有几处结构性断点：大多数课实际上发不出收益，却没有任何报错。此后每轮修完，下一轮又能在新代码与老代码的交界处找到问题。

每一轮查出的问题有一个共同点：**单看一个函数都对，放进行为循环、跨天结算、改岗、成年这些真实时序里才会出错**。所以复查不能只读代码，要推演时序，还要用无头复现证明问题真的存在。

## 3. 一轮的流程

```
建档与基线
  编号 / 轮次 / 快照 → 系统档案 → 已知清单 → 回归基线 → 符号引用核查
        │
        ▼
核查与复现
  按检查维度通读源码与挂接点 → 逐条对抗式核实（默认反驳）
  → 补漏复核 → 写无头复现脚本并实跑确认
        │
        ▼
定级与方案
  分级 H / M / L → 拟定口径 → 写进 PR 说明（长表放 PR 评论或链接文件）→ 中文确认口径
        │
   【停止点 1：确认口径】
        │
        ▼
实施与回归
  回写口径、先改共用文件 → 逐项实施并复核改动
  → 全套回归 → 方案对照 / 测试覆盖 / 改后复现核对
        │
        ▼
收尾与归档
  说明文档 / 测试 README → update.log → PR 说明记下本轮发现、口径与回归计数
        │
   【停止点 2：确认提交信息】→ 提交
```

复查底线：每条写进方案的发现都要亲自核对源码与复现证据，不直接采信未经核实的二手结论。

## 4. 产出物与生命周期

| 产出 | 生命周期 |
| --- | --- |
| 复查记录 | PR 说明（记录本轮要点）＋PR 评论或链接文件里的发现表、复现 R 组表、回归计数；合并后以 PR 为准 |
| 复现脚本 | 临时脚本，会话结束即丢；R 组表写全在 PR 评论或链接文件，丢了照表重建 |
| 系统说明文档 | 受影响的章节同步新规则；「维护注意事项」每轮新增踩过的坑 |
| 回归套件 | 每轮新增断言；新夹具陷阱写进套件 README |
| `update.log` | 按玩家视角登记，改前算 BUG 的归「修正」 |

## 5. 经验

1. **按代码 token 统计引用比文本 grep 严**：文本 grep 会被注释与字符串里的同名词骗过，统计标识符引用时应按语法 token 核查。
2. **「排查过、没有发现问题的疑点」要落表**：不落表的话，下一轮会有人把同一个误报再查一遍，把已排除项记进已知清单可避免重复核查。
3. **死内容要配校验规则**：Plan 30 修期末 9 / 10 的同时给 `tools/official_event_check.py` 加了「期末桶禁用本学期数值」的规则，防止以后写新事件再踩。
4. **测试夹具必须与真实数据对齐**：夹具让婴儿进了 `npc_id_got`，婴儿期事件一条都派不出来的问题八轮复查都没测出来（说明文档 §15 第 20 条）。
5. **复现脚本要有对照项**：只有「问题命中」的脚本，改后不成立可能只是夹具没走到那条路径。
6. **口径拍板一次就不再问**：用户按设计保留的（Plan 27 L2）、改判的（Plan 29 §8.1），都进已知清单。
7. **复查结论必须逐条对照源码核实**：排查与复核过程都可能看错行号、漏看守卫；写进方案的每条发现都要亲自核对源码与复现证据。

## 6. 何时停止复查

满足以下全部条件时，不再开新一轮，剩余的低级项写进 todo：

- 一轮只有低级（L）发现
- 复现脚本里没有「问题命中」项（发现都是文档与卫生类）
- 死代码扫描零引用只剩注册式

反过来，系统有新的功能改动（新口径、新数据）之后，再开一轮。
